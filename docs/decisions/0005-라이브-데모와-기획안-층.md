# 0005. 라이브 데모, 실제 수집(YouTube), 마케터용 기획안 층

- 상태: 채택 (2026-11-24)
- 계기: 지원자 요구
  - 제출할 때 AI를 포함한 모든 동작이 라이브로 실행되어야 한다
  - 무엇을 위한 서비스인지 바로 이해되어야 한다
  - 수집 결과를 AI가 기획으로 바꾸고, 마케터가 진행 여부를 고르는 흐름이 있어야 한다

## 검토 방법: 페르소나 5 × 전략안 6 = 시뮬레이션 30회

다섯 명의 페르소나가 각자 6개 전략안으로 서류를 받았을 때를 시뮬레이션했다.
- 페르소나: 삼양 글로벌 마케터, 인사담당자, AX팀 엔지니어, 사업전략팀, 취업 컨설턴트
- 시뮬레이션 항목: 처음 30초에 본 것, 감점 지점, 가점 지점, 통과 확률

| 전략 | 인사 | 마케터 | AX | 사업전략 | 컨설턴트 | 평균 |
|---|---|---|---|---|---|---|
| S4 수집 + AI 기획 + 실제 라이브 소스 | 85 | 82 | 78 | 68 | 55 | **73.6** |

### 페르소나 사이에 합의된 것

- **원본 기능을 메뉴로 늘어놓지 않는다.** S3는 다섯 명 모두 최하위로 꼽았다. 초점을 잃고, 이전 직장 산출물을 반출했다는 의심을 받을 수 있다는 이유다.
- **마케터는 "다음에 무엇을 수집할지"를 결정할 이유가 없다.** 마케터가 시간을 쓰는 일은 본 것을 기획으로 바꾸는 일이다(마케터).
- **MCP는 마케터용이 아니다.** "마케터는 웹, 엔지니어와 AI 도구는 MCP"로 사용자를 명시하면 오히려 강점이 된다.
- **해시태그는 주제이고, 기획 단위는 포맷이다**(사업전략).
- **원본에서 살릴 것은 D+3/D+7 성과 판정**이다. 채택한 기획안의 성공 기준으로 쓴다.
- **하지 말 것**
  - 실존 브랜드에 수치를 붙이는 것
  - "AI가 바이럴을 예측한다"는 주장
  - 가상 데이터로 만든 효과 수치

### 의견이 갈린 곳과 판정

- **기획 층의 두께**: AX팀은 "가상 데이터 위의 기획은 검증할 수 없는 면적만 늘린다. 두껍게 하면 65%"라고 했다.
  → **얇게 간다.** 기획안 한 종류만 만들고, 기존 가드·승인 구조를 그대로 재사용한다.
- **YouTube 재도입**: 컨설턴트와 사업전략팀은 "0001에서 기각한 것과 모순된다"고 지적했다. → 아래 "0001 뒤집기"에 이유를 적는다.

## 결정

### 1. 라이브 데모 서버 (`apps/collector/src/live`)
- 웹과 API를 한 서버에서 제공한다.
- 방문자마다 시드 DB의 메모리 사본(샌드박스)을 준다. 각자 AI를 호출하고 승인·실행해도 다른 방문자에게 영향이 없다.
- Claude 호출 예산을 둔다: 방문자별, 하루, 동시 호출 상한. 상한을 넘으면 녹화 응답으로 대체하고, 그 이유를 화면에 보여준다.
- 배포는 Render(Docker)로 한다. Vercel 서버리스는 요청 사이에 메모리 상태를 유지할 수 없고, 네이티브 SQLite와 Chromium도 맞지 않는다.

### 2. 실제 수집: YouTube Data API v3 (0001 뒤집기)
- **0001에서 기각한 이유**: "대상 플랫폼이 아니라 주력 소스로 쓰면 공고를 안 읽은 것처럼 보인다."
- **지금 들이는 이유**: 지원자가 "실제 수집이 돌아가는 것"을 요구했다. 그리고 공식 API로 지금 바로 실제 데이터를 받을 수 있는 숏폼 소스는 YouTube뿐이다.
  - TikTok Research API는 연구 기관 승인이 필요하다.
  - Instagram은 지원자의 Meta 앱과 비즈니스 계정이 필요하다.
- **주력이 아니라 "실제 동작 증거"로 쓴다.** TikTok·Instagram 어댑터와 녹화 응답은 그대로 둔다.

#### YouTube 정책을 코드로 지킨다
출처: Developer Policies 원문, 2026-11-24 확인.

| 정책 | 코드 |
|---|---|
| III.E.4: 저장 30일이 지나면 갱신하거나 삭제 | `purgeExpiredYouTube`: 수집할 때마다 실행 |
| III.E.2: 소유자가 다른 API 데이터를 합치지 않음 | 해시태그·동시출현·포맷 집계에서 YouTube를 뺀다 (`platform <> 'youtube'`) |
| III.E.4.h: 파생 데이터·지표를 만들지 않음 | YouTube 영상은 영상 단위 사실(`video:youtube:<id>`)로만, YouTube가 준 값 그대로 쓴다 |
| III.I.4: 링크를 제거하지 않음 | YouTube 행은 원본 링크로 연결하고 "YouTube 제공"으로 표시한다 |
| 쿼터: search.list 하루 100회, 태평양 시간 자정 초기화 | 가드의 quota 검사로 하루 80회 상한을 둔다. 쿼터 소진은 재시도하지 않는 `quota_exhausted`로 분류한다 |

- AX 페르소나는 "search.list는 100단위"라고 했지만, 문서를 확인하니 지금은 별도 버킷에서 1단위, 하루 100회였다. **에이전트의 주장을 1차 자료로 고쳐 반영했다.**
- 정책의 Authorized/Non-Authorized Data 정의(정책 IV)는 읽지 않았다. 어느 쪽이든 30일 규칙은 같아서 가장 보수적으로 적용했다.

### 3. 마케터용 기획안 (`content_brief`)
- Claude가 기획안을 낸다. 기획안의 내용은 다음과 같다.
  - 포맷 사실(`format:*`)을 근거로 인용한다
  - `plan`: 포맷, 훅, 산출물, 성공 기준(D+7), 브랜드 위험
- 기존 가드를 그대로 거친다. 근거·수치 대조, 포맷 일치(target), 같은 포맷 중복, 마케터가 7일 안에 거절한 포맷을 검사한다.
- 마케터가 채택하면 승인 상태(실행 백로그)로 남는다. **수집은 실행하지 않는다.** 거절 사유는 다음 계획에 반영된다.
- 포맷은 LLM이 아니라 공개된 규칙으로 분류한다(`core/format.ts`). 같은 입력이면 같은 결과가 나와야 설명할 수 있기 때문이다.

### 4. 첫 화면을 마케터 언어로
- "지금 뜨는 숏폼 포맷을 찾아 근거가 검증된 기획안으로 만드는 에이전트"
- "누가 무엇을 쓰나"를 명시한다: 마케터는 웹, 엔지니어와 AI 도구는 MCP

## 확인한 것

- 지원자 키로 실제 Claude(claude-opus-5-5)를 6회 호출하며 전체 흐름을 확인했다.
  - 마지막 실행 결과: 21초, 제안 4건 모두 통과. 기획안 1건을 마케터가 채택했고 수집 실행 수는 그대로였다.
  - 그 과정에서 실제 출력에서만 드러나는 문제 5가지를 찾아 고쳤다 (0002 §8).
- YouTube 어댑터는 공식 문서 형식의 녹화 응답으로 테스트했다.
- **실제 YouTube 호출은 아직 검증하지 못했다.** 지원자의 YOUTUBE_API_KEY가 필요하다.

## 한계

- 실제 YouTube 오류 응답의 JSON 형식은 문서에서 확인하지 못했다. Google API 공통 형식을 가정했다.
- Render 무료 플랜은 15분 동안 요청이 없으면 잠든다. 깨어나는 데 1분 정도 걸리므로, 제출 기간에는 유료 플랜(starter)이나 사전 접속을 권한다.
- 기획안의 "좋고 나쁨"은 가드가 판단하지 않는다. 그 판단이 마케터의 몫이다.
