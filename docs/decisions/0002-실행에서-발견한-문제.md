# 0002. 실행해 보고서야 드러난 문제들

- 상태: 모두 수정, 회귀 테스트 있음 (2026-11-24)

코드를 쓰고 타입 검사와 단위 테스트를 통과한 뒤에도, 실제로 실행해 보니 드러난 문제들이다.
"테스트 통과 = 동작"이 아니라는 기록이다.

## 1. 좋아요를 숨긴 게시물이 통째로 버려짐

- **증상**: `npm run demo:fail`을 실행했다. Instagram 실행 #2에서 1건, #7에서 8건 전부가 "게시물 형식 오류"로 제외됐다. #7은 "좋아요 필드가 사라지는 구조 변화"를 감지해야 하는 시나리오였다. 그런데 저장된 게시물이 0건이라 감지 자체가 일어나지 않았다.
- **원인**: Instagram은 소유자가 좋아요를 숨기면 `like_count` 필드 자체를 뺀다. 이 필드를 zod v4 `z.looseObject({ like_count: z.unknown() })`로 검증하고 있었다. zod v4에서는 `z.unknown()`도 키가 없으면 실패한다.
- **의미**: 원본의 "미수집 → 0" 버그를 고치려다 "미수집 → 게시물 전체 폐기"라는 더 나쁜 버그를 만들었다. 단위 테스트는 좋아요가 있는 픽스처만 썼기 때문에 통과했다.
- **수정**: 모든 지표 필드를 `.optional()`로 바꿨다.
- **확인**: 회귀 테스트("좋아요를 숨긴 게시물을 버리지 않고 likes=null로 저장한다")를 추가했다. 수정을 되돌리면 이 테스트가 실패하는 것도 확인했다.

## 2. TikTok int64 ID 정밀도 손실

- **발견**: 공식 문서의 응답 예시 `video_id: 702874395068494965`가 2^53(약 9.007e15)보다 크다는 것을 확인했다.
- **원인**: `JSON.parse`는 이 값을 double로 바꾼다. 예를 들어 `7300000000000000001`은 `7300000000000000000`이 된다. 그러면 서로 다른 영상이 같은 저장 키를 갖게 된다.
- **수정**: 파싱 전에 `id`와 `video_id` 필드의 숫자를 문자열로 감싼다 (`parseJsonPreservingIds`).
- **확인**: 저장된 DB 값을 직접 조회해 `...001`과 `...002`가 따로 저장된 것을 봤다. 테스트에서는 일반 `JSON.parse`가 값을 바꾼다는 전제부터 확인한다.

## 3. 어댑터별 오류 집계가 틀림

- **발견**: SQL을 다시 읽다가 찾았다.
- **원인**: 실행별 `(kind, count)`를 `json_group_object`로 묶었다. 같은 kind가 여러 실행에 걸쳐 있으면 JSON에 같은 키가 여러 번 들어가고, `JSON.parse`는 마지막 값만 남긴다. 그 뒤에 TS에서 합산하는 함수를 붙였지만, 파싱 시점에 이미 값이 사라진 뒤라 의미가 없었다.
- **수정**: CTE에서 `(adapter_id, kind)`로 먼저 `COUNT`한 다음 객체로 묶는다.
- **확인**: 데모 시나리오 전체 테스트에서 `server: 4`(503 네 번)를 검사한다.

## 4. 브라우저 수집이 모두 실패

- **증상**: 브라우저 데모를 처음 실행했을 때 v1·v2·v3이 모두 `ReferenceError: __name is not defined`로 실패했다.
- **원인**: tsx(esbuild)는 함수 이름을 보존하려고 `__name()` 헬퍼를 코드에 끼워 넣는다. `page.evaluate`에 넘긴 함수는 문자열로 직렬화되어 브라우저에서 실행되는데, 브라우저에는 이 헬퍼가 없다.
- **수정**: evaluate 안에서 이름 붙은 내부 함수를 만들지 않는다.
- **덤**: 이 실패도 실행 기록에 `fetch / unknown / 오류`로 남았다. 실패를 숨기지 않는다는 설계가 의도대로 동작한 셈이다.

## 5. 예상 못 한 예외가 나면 다음 실행이 영구히 막힘

- **발견**: 코드 리뷰에서 찾았다.
- **원인**: DB 오류 같은 예상 밖 예외가 나면 실행이 `running` 상태로 남는다. 그러면 부분 UNIQUE 인덱스가 같은 쿼리의 다음 실행을 계속 막는다.
- **수정**: 실행 본문을 try/catch로 감싸고, 예외가 나도 `failed`로 마감한 뒤 다시 던진다.
- **확인**: 파서가 TypeError를 던지게 만든 뒤, 다음 실행이 성공하는지 확인하는 테스트를 추가했다.

## 6. 상태 판정 기준

- **문제**: 처음에는 "받은 페이지가 있으면 partial"로 판정했다. 그런데 브라우저 v3처럼 페이지는 받았지만 파싱에서 막혀 아무것도 얻지 못한 경우도 partial로 표시됐다.
- **수정**: "받은 항목이 있으면 partial, 없으면 failed"로 바꿨다.
