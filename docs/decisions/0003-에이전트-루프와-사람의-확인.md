# 0003. 에이전트 루프: LLM 제안 · 결정적 가드 · 사람의 확인

- 상태: 채택 (2026-11-24)
- 계기: 지원자 검토 의견. "LLM을 활용한 제안, 수식(로직)의 할루시네이션 방지, 사람의 컨펌 구조로 에이전트가 동작하는 부분이 있는가? 이 서비스를 에이전트 서비스라고 할 수 있는가?"

## 자기 평가 (변경 전)

| 질문 | 답 |
|---|---|
| LLM이 판단에 쓰이는가 | 아니오. LLM 호출이 하나도 없었다 |
| 시스템이 스스로 다음 행동을 정하는가 | 아니오. 사람이 정한 쿼리를 결정적 파이프라인이 실행할 뿐이었다 |
| 사람의 확인 단계가 있는가 | 아니오 |
| MCP | 읽기 전용 조회 도구만 있었다 |

결론: "수집 파이프라인과 조회 API"였고, 에이전트라고 부를 수 없었다. AI Agent Builder 지원작으로는 가장 큰 공백이었다.

## 결정

에이전트 루프를 하나 넣는다: **관찰 → LLM 제안 → 가드 → 사람의 결정 → 실행 → 기록**.

1. **관찰** (`agent/observation.ts`): DB에서 사실 목록(fact)을 만든다. 모든 값은 SQL로 계산하고, 사실마다 `factId`를 붙인다.
2. **제안** (`agent/planners.ts`): LLM이 다음 행동을 제안한다. 종류는 세 가지다: 새 수집, 실패 실행 재시도, 사람이 할 운영 조치.
   - 근거는 `factId`로만 인용한다.
   - 숫자는 `claims: {factId, field, value}`로 따로 적는다.
   - Claude API 구조화 출력(`betaZodOutputFormat`)으로 형태를 강제한다.
   - 키가 없을 때는 녹화한 계획 응답으로 돌린다.
3. **가드** (`agent/guard.ts`): 7개 검사를 결정적으로 수행한다. 하나라도 실패하면 `blocked`가 되고 사람에게 승인 요청이 가지 않는다.
   - **schema**: 형식이 맞는가
   - **evidence**: 인용한 사실이 관찰 목록에 있는가
   - **claims**: 수치 주장이 SQL 값과 정확히 같은가
   - **grounded_numbers**: 제목·근거 문장에 쓴 숫자가 인용한 사실의 값인가. claims를 우회해 문장에 숫자를 끼워 넣는 것을 막는다
   - **capability**: 어댑터가 그 검색을 지원하는가 (Instagram은 해시태그만 가능). 재시도 대상이 실제로 실패한 실행인가
   - **duplicate**: 검토 중인 같은 제안이 있는가. 최근 24시간 안에 같은 쿼리를 수집했는가
   - **quota**: Instagram 7일 고유 해시태그 30개 한도를 넘지 않는가
4. **사람의 결정** (`agent/review.ts`): 승인, 거절(사유 필수), 확인(운영 조치) 중 하나를 고른다. 검토자 이름이 없으면 결정할 수 없다.
5. **실행**: 승인하는 순간 가드를 **다시** 돌린다(TOCTOU). 제안이 만들어진 뒤 상황이 바뀌었다면 실행하지 않고 `blocked`로 되돌린다.
6. **기록**: `agent_proposal` 테이블 한 행에 다음을 모두 남긴다.
   - 제안 내용과 제안자(`proposed_by`)
   - 가드 결과
   - 검토자, 사유, 시각
   - 실행 결과(`result_run_id`)

   DB CHECK 제약이 앱 코드를 우회한 경우도 막는다. 사유 없는 거절, 검토자 없는 결정, 실행 기록 없는 "실행 완료"는 DB가 받지 않는다.

### 사람의 확인을 어디서 하는가
- **CLI**: `agent approve|reject|ack`
- **웹**: 로컬 검토 API(`serve.ts`, 127.0.0.1 전용) + 제안 검토 화면. `npm run dev:live`로 실행한다. 정적 배포(GitHub Pages)에서는 읽기 전용이다.
- **MCP**: `observe`, `propose_action`만 공개한다. **승인 도구는 일부러 두지 않는다.** 외부 AI(Claude Code 등)도 계획자 역할을 할 수 있지만, 결정은 사람만 한다.

## 고려했지만 택하지 않은 것

| 안 | 택하지 않은 이유 |
|---|---|
| Managed Agents / 도구 호출 루프로 LLM이 직접 수집을 실행 | 수집은 쿼터와 약관이 걸린 외부 호출이다. 모델이 도구 호출을 이어가며 직접 실행하게 하면 실행 전에 사람이 확인할 지점이 사라진다. 이 기능의 루프는 코드가 통제하고, LLM은 "제안" 한 단계만 맡는 워크플로가 맞다 |
| LLM에게 수치를 직접 쓰게 하고 사후에 사람이 확인 | 사람이 매번 숫자를 대조하는 것은 비효율이고 놓치기 쉽다. 대조는 기계가, 판단은 사람이 한다 |
| 가드 없이 낮은 temperature, 프롬프트 지시만 | 프롬프트는 확률을 낮출 뿐 보장하지 않는다. 녹화 응답의 할루시네이션 3건은 프롬프트를 지켰더라도 생길 수 있는 유형이다 |
| HTTP 서버 없음 (0001의 결정) | **뒤집었다.** 사람의 확인을 화면에서 하려면 쓰기 경로가 필요하다. 127.0.0.1에만 열고 정적 배포에는 넣지 않는 것으로 범위를 제한했다 |

## 확인한 것

- 녹화 응답 6건 → 3건 통과, 3건 차단. 차단된 3건은 다음과 같다.
  - 없는 근거와 지어낸 수치
  - 수치 부풀림(57 → 120)과 지원하지 않는 검색
  - 중복
- MCP 클라이언트로 실제 연결해 확인했다. 정확한 근거를 인용한 제안은 `pending`, 숫자를 10에서 500으로 부풀린 제안은 `blocked`와 이유가 돌아왔다.
- 웹 화면에서 Playwright로 승인을 눌러 봤다. 재검증을 거쳐 실행 #12가 생기고, 검토자가 기록됐다.
- 테스트 18개(`test/agent.test.ts`). 수치 대조와 승인 시점 재검증을 각각 꺼 보면 해당 테스트가 실패하는 것을 확인했다.

## 한계

- Claude 계획자(`claudePlanner`)는 이 환경에 API 키가 없어 실제 호출로 검증하지 못했다. 요청 형식은 SDK 타입 검사를 통과했고, 출력은 녹화 응답과 같은 가드를 거친다.
- 가드는 "근거와 숫자가 데이터와 맞는가"를 보장할 뿐, "좋은 제안인가"는 판단하지 않는다. 그 판단은 사람의 몫으로 남겼다.
- 문장 속 숫자 검사는 형식에 기댄다. "열두 건"처럼 한글로 쓴 숫자는 잡지 못한다.
